# v1.1.0

Released 2026-10-27. 52 commits since `v1.0.0`, on `develop`, merged to `main` for this tag.

## What this release is

**The `kwisatz` CLI is now the entry point.** Every command that used to mean "read the
README, find the script, remember the environment" is a subcommand with a `--json` document
and a documented exit code, and the CLI runs the same `deploy.py` pyinfra deploy that a bare
run of the orchestrator runs — one engine, not a second implementation beside it.

`run-setup.sh` is **gone** (see *Removed* below). That is the only removal in this release,
and the only reason a v1.0.0 user's habits have to change.

## New: the `kwisatz` CLI

| Command | What it answers |
|---|---|
| `kwisatz install` / `kwisatz init` | put `kwisatz` on `PATH`; create `machine-config.yml` and run `doctor` |
| `kwisatz apply [TARGET]…` | one, several, or every enabled target, in config order |
| `kwisatz status` | the plan, in run order, with env values masked — runs nothing |
| `kwisatz list [--all]` / `kwisatz info <target>` | what can be installed; one target's help, command, env and last apply |
| `kwisatz doctor` | is this box ready (OS, sudo, uv, python, docker, GPU, ports, `/srv` space, the §6.5 table) |
| `kwisatz config show\|validate\|enable\|disable\|set\|unset\|args\|path\|init` | edit `machine-config.yml` without an editor — comments stay byte-identical |
| `kwisatz services` / `kwisatz logs <target>` / `kwisatz state` | what is running now, whose logs, and what was applied last |
| `kwisatz models sync\|status\|show` | the model catalog, through the tool that owns it |
| `kwisatz run <target> -- …` | arguments the CLI is not allowed to guess |
| `kwisatz commands --json` | the whole CLI surface as data, for an agent that must not read docs |

Two rules the release commits itself to, because both were already broken once in the
window this release covers:

- **Exit codes are a contract.** `0` success · `1` a script failed · `2` bad usage · `3`
  config · `4` prerequisite · `5` unhealthy stack or `--timeout` · `8` `--keep-going`
  finished with failures · `9` lock held. `6` and `7` are published and deliberately never
  emitted; a machine consumer should branch on these, not on message text.
- **Single-target apply cannot install something different from a full one.** Both start the
  same `deploy.py`; `tests/unit/test_conformance.py` and `test_deploy_engine.py` assert what
  the *task script* receives (argv, env, stdin, ancestry), so a change that quietly execs the
  script itself fails the suite.

## Removed: `run-setup.sh`

The deprecated shim is deleted rather than deprecated harder, which is what `R-ARCH-103` said
would happen (`docs/features/kwisatz-cli-specification.md` §11.3). In one sentence:

| Used to run | Now |
|---|---|
| `./run-setup.sh status` | `./kwisatz status` |
| `./run-setup.sh apply` | `./kwisatz apply` |
| `./run-setup.sh apply --data config=path/to/other.yml` | `./kwisatz apply --config path/to/other.yml` |

The exit-code change the deprecation documented still applies: `status` on an unparsable
config exits `3` (CONFIG) where a bare pyinfra run exited `1`. Nothing else changed for
anyone who calls pyinfra directly — `uv run pyinfra @local deploy.py …` is still the engine
and still documented.

## Changed: `apply` settles sudo before the first script runs

Every task script escalates with `sudo`, and none of them can answer a password prompt: the
deploy runs its children with `/dev/null` on stdin, and `sudo` reads a password from the
controlling terminal rather than from stdin. Before this release a box whose `sudo` needs a
password did not fail politely — the first script died inside gevent with `termios.error` →
`EOFError`, exit `1`, and a hint to retry the target that had just failed.

`apply` now checks the ticket the way a script would, asks once with `sudo -v` on your own
terminal when it is missing (`sudo -A -v` when `SUDO_ASKPASS` is exported), and holds it open
with `sudo -n true` every 3 minutes for the rest of the run. `--json` runs never prompt;
`--no-sudo-warmup` leaves sudo alone. When no ticket is obtainable the run stops before the
first script with `4` and the reason.

Two consequences worth knowing:

- Scripts run in their own **process group** but the **same session** as your terminal. The
  process group is what the `--timeout` kills; the session is what lets the ticket you primed
  reach them. (`start_new_session=True` used to break that half silently.)
- If the message says the ticket found is not one the scripts can use, `sudo -v` again cannot
  fix it: run the apply from the login terminal that primed it, or make the ticket
  session-independent with `Defaults timestamp_type=global` in `/etc/sudoers.d`.

`kwisatz doctor`'s `sudo` check reports both probes, so the two commands cannot disagree
about the same box.

## New service: `setup-music-gen`

ACE-Step 1.5 song generation — a GPU server mode, plus CPU preview modes so the stack can be
tried without a card. Ships disabled; `MUSIC_GEN_MODE` (`server`, default) and
`MUSIC_GEN_PORT` (`9294`) drive it, and re-running converges the way every other task does.

```yaml
  setup-music-gen:
    enabled: false
    description: Install ACE-Step 1.5 song generation (GPU) or CPU preview
    env:
      MUSIC_GEN_MODE: server
      MUSIC_GEN_PORT: '9294'
    args: []
```

## Changed: the orchestrator is a pyinfra deploy

`apply` runs each resolved target as `deploy.py -y -vvv --data select=<name>`, which is the
same command line the whole-config deploy has always had, narrowed to the targets it asked
for. Consequences are documented rather than hidden: pyinfra is a run-time prerequisite (`uv`
or the checkout's venv, otherwise `4`), a target costs about a second of deploy startup, and
the script's own output arrives on **stderr** because that is where pyinfra's `-vvv` report
goes — so the per-target `logs/kwisatz-<utc-ts>-<target>.log` (mode `0600`) is what `kwisatz
logs <target>` reads after an exit `1`, and `--interactive` / `kwisatz run` are the paths where
the script's stdout is stdout.

A `--timeout` that runs out is now honest: the target is `not-run`, not `failed`, and the run
exits `5` even with `--keep-going` — a run the deadline stopped did not finish.

## NetBird

The routing peer is enrolled properly (`exposedAddress` published with `:443`) and its setup
key is persisted, so a re-run reuses the key it enrolled with instead of minting a new one.
The whole LAN/routing-peer flow is documented in `README_NETBIRD.md`, with the
`skills/netbird` skill for the CLI/API detail behind it.

## Tooling and tests

- `tests/git-hooks/pre-commit` is a versioned lint gate (`tests/install-git-hooks.sh`): the
  linting `AGENTS.md` asks for runs over the **staged** content of every commit, and a missing
  linter fails the commit instead of skipping.
- The VM suite drives `./kwisatz` rather than a wrapper, and its `--mode script` precheck runs
  the CLI too.
- `tests/lint.sh` gained guards that lint what the VM suite cannot see: both shipped example
  configs must parse through the CLI, and every config key must name a real
  `tasks/<name>.sh|py` entry point.
- Coverage is measured where the CLI actually runs (`bash tests/coverage.sh`), because a
  `pytest --cov` on a subprocess-driven CLI reports `cli.py` at 0 %.
- Unit suite: 186 tests, including the two conformance tests above, the timeout budget, the
  exit-code documents, and a sudo-priming suite that no longer depends on the sudoers of
  whatever machine runs the tests.

## Config file

Nothing breaking. One new disabled entry (`setup-music-gen`, above) and the netbird keys
(`NETBIRD_DOMAIN`, `NETBIRD_HOME`) as they were. The `.scripts.<name>` contract
(`enabled` / `env` / `args`, `description` informational) is unchanged; `args:` and `env:`
may now be null and are read as empty. `requires:` and `group:` are spec proposals, **not**
implemented — the spec mentions them as additive options and the code has no idea what they
mean yet.

## Upgrade notes

1. `./kwisatz install` (or call `./kwisatz` from the checkout) once, then `./kwisatz status`
   to read the box before changing anything. `run-setup.sh` will not come back.
2. If your automation called `run-setup.sh` from CI, that job needs its two argument
   substitutions from the table above; a job that called pyinfra directly is unaffected.
3. Expect one `sudo` prompt up front on a box with passwordful sudo, and a `4` — not a `1`
   and a traceback — where a closed stdin used to eat the run.
4. If `kwisatz --version` and the `VERSION` file ever disagree, `VERSION` and the tag are the
   release; `__init__.py` is the runtime copy that has to be bumped in the same commit.

## What was *not* verified in this release

The static and unit gates ran for this release: `tests/lint.sh` (all guards green), `ruff`,
`shellcheck` over every changed task and `lib/strix-halo-helper.sh`, `yamllint`, and
`pytest` at 186 passed.

The VM-based integration/idempotency suite (`tests/run-vm-tests.sh`, 15–30 min) was **not**
run for the tasks this release changes — `setup-music-gen`, `setup-netbird`, `setup-pi`,
`setup-strix-halo-tuning`, `setup-unsloth` and `lib/`+`templates/netbird/`. It needs privileged
libvirt (`virt-runner`), and no passwordless sudo is available in this session, so the run was
not possible rather than skipped. Treat the VM verdict for those scripts as *carried over from
their own branches*, not from this release commit. `setup-music-gen` in particular has never
been run here at all.

## Versioning and requirements

`VERSION` (1.1.0) and the annotated tag `v1.1.0` are written in this same commit and carry the
same value; `src/kwisatz/__init__.py` is bumped alongside them because `kwisatz --version`
prints that one. Semver is defined by what the user of this repo touches: **MAJOR** = breaking
`machine-config.yml` keys, removed/renamed `tasks/` scripts, or a breaking change to the CLI
(commands, flags, `--json` envelope, exit codes); **MINOR** = a new `tasks/` script or a new
config option; **PATCH** = fixes. This is MINOR: `setup-music-gen` is a new script and the CLI
surface is additive. Note one judgement call: `run-setup.sh` was *removed*, which is why this
could be argued as MAJOR — the repo's rule counts removals under `tasks/` and CLI changes, and
the deletion had been promised as of its deprecation, so 1.1.0 is the letter of the rule. If
that reads too lenient, 2.0.0 is the honest number for the next time it matters.

Ubuntu with systemd, `ufw`, docker. `uv` is now a prerequisite of the orchestrator (the CLI
installs it with `kwisatz install --with-uv`); pyinfra is fetched into the checkout's `.venv`
on first run. Tasks still run as the invoking user, with `sudo` for the privileged steps.
