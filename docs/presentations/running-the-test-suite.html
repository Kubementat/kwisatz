why this suite looks strange

We test a machine, not a function

kwisatz is ~60 task scripts plus a CLI that runs them through pyinfra. Their contract is two sentences long:

1. On a clean Ubuntu server, kwisatz apply leaves a working service.

2. Running it again converges — reuses secrets, keeps data, never tears down.

Rule 2 is the one humans forget, and it is the one that bites in production.

So the suite is a machine, not a mock

A throwaway KVM guest is created per run, the whole checkout is copied in, every enabled script is executed twice, and the report shows the full matrix. Nothing on your host is touched, and no VM survives the run.

the four layers

Cheap and boring first, expensive and real last

Static analysis~secondsshellcheck · ruff — the primary gate
Repo guards~1 stests/lint.sh — 6 guards the VM suite structurally cannot see
Unit · CLI · conformance~12 suv run pytest — 114 tests
VM integration + idempotency15–30 mintests/run-vm-tests.sh

Work bottom-up while iterating; the VM suite is the last gate before a merge, not the first thing you run. The pre-commit hook already runs the top two for you.

Order matters for cost: lint is sub-second, pytest ~12 s, VM suite 15-30 min. The pyramid is inverted on purpose (widest = cheapest).

layer 1 · static analysis

Lint every file you touch

bash
shellcheck tasks/setup-traefik.sh lib/helpers.sh   # every .sh, no errors or warnings
uv run ruff check src tests deploy.py              # the python side
jq empty some.json                                 # .json / .js
yamllint -d relaxed machine-config.yml.example     # .yml / .yaml

AGENTS.md rule: lint every created or modified file. shellcheck is the repo's primary quality gate — most "the script broke the box" bugs are quoting, unchecked cd, and unset variables, and it finds them in milliseconds.

Do it automatically

tests/install-git-hooks.sh installs a pre-commit gate that lints the staged content of exactly these file types. Slide 17.

layer 4 · the VM suite

One run = 2·N + 1 test cases

PhaseWhat happens on the guestPass =
precheck./kwisatz status --config <test-config>exit 0
integrationfirst run of each target on the clean VM, in config order, with its configured env:/args:exit 0

Default config: 10 fast, safe, non-interactive scripts → 21 cases. A failing script never stops the run: you always get the whole matrix.

layer 4 · vm suite shape7
once per host

Prerequisites: one command

bash
./tasks/setup-virt-runner.sh          # clones virt-runner, installs KVM/libvirt/pools, uv tool install, verifies
virt-runner list                       # must work without sudo

Host checklist

Ubuntu with /dev/kvm · libvirt usable without sudo · storage pool vm-pool active · NAT network default active (dnsmasq, 192.168.122.0/24) · scp, jq, yq on PATH · uv for the CLI

SSH key + overrides

Public key injected into the guest: ~/.ssh/id_ed25519.pub, override with VM_SSH_KEY.
virt-runner command on PATH is virt-runner, override with VIRT_RUNNER.

Preflight fails fast and creates no VM if any of this is missing — you get a message, not a half-built guest.

Remember: only the VM create path must run without sudo. Everything inside the guest is sudo by design.

run it9
anatomy of one run

What happens between run-vm-tests.sh and the report

0 · PREFLIGHT
Fail before creating

virt-runner + jq present, libvirt reachable, test config and SSH key readable. --scripts generates a one-off config (env/args preserved).

1 · CREATE
virt-runner create --json

Fresh Ubuntu guest mas-vmtest-<ts>, cloud-init injects the key, DHCP lease + real SSH round-trip verified; 5 min extra retry for slow boots.

2 · COPY
scp the checkout

repo → /home/<user>/kwisatz, active config → /tmp/test-config.yml.

3 · BOOTSTRAP
yq, jq, uv

apt install on the guest; uv to /usr/local/bin so ./kwisatz works in a non-login ssh session.

4 · RUN
tests/remote/run-tests.sh

One SSH session: precheck → integration → idempotency, each under sudo -u <user> timeout, writing results.jsonl + a log per case.

5 · FETCH
/tmp/vmtest → host

results.jsonl, meta.json and every log land in the report directory.

6 · REPORT
report.md

script × phase table with durations, precheck, verdict, links to all artifacts.

7 · TEARDOWN
virt-runner destroy

destroy + undefine + delete <name>_vda.qcow2. Runs from the EXIT trap too, so early failures never leak a VM.

The guest is named mas-vmtest-<timestamp> and teardown touches that domain and its volume only — your other VMs are never at risk.
Each case runs as the VM user under `sudo -u`, which re-initialises supplementary groups: without it, `usermod -aG docker` from an earlier case would stay invisible in the long-lived SSH session and break every later docker call.
anatomy10
two ways to run one case

--mode cli vs --mode script

cli default

./kwisatz apply <target> — a real pyinfra deploy of the copied checkout (deploy.py -y -vvv --data select=<target>).

Under test: the entry point, target resolution, the config's env:/args:, INTERACTIVE=false, /dev/null stdin. This is what operators and agents run, so this is what counts.

script fallback

sudo -u <vm-user> env … ./tasks/<name>.sh <args> — the bare script.

The runner re-implements entry-point and env/args resolution with yq+jq, which is exactly why it is not the default. Use it to bisect: a case failing in cli but passing in script is a dispatch bug, not a script bug.

bisect a failure
tests/run-vm-tests.sh --scripts setup-traefik                # fails → is it the script or the dispatch?
tests/run-vm-tests.sh --scripts setup-traefik --mode script  # passes → dispatch; fails → script
Use script mode to bisect: script passes but cli fails is a dispatch bug, not a provisioning bug.

Verdict vocabulary

PASS (Ns)exit 0 in that phase
FAIL (rc=N)the script's own exit code
rc=125no tasks/<name>.sh / .py — typo in config or --scripts
TIMEOUT (Mm)rc=124, raise --timeout

Exit codes of the harness

0every case passed
1a case failed or the pipeline itself did (VM create, scp, …)
2usage error
Exit code 1 covers both a failing case and a failing pipeline - always read the verdict table.

The three commands that answer most failures

bash
R=tests/reports/vmtest-<ts>
tail -60 $R/vmtest/logs/integration-setup-traefik.log
jq 'select(.rc!=0)' $R/vmtest/results.jsonl
jq -r '.error' $R/create.json

The last lines of every failing script are also echoed to the console at the end of the run — you rarely need to open the file at all.

logs are chmod 644 deliberately so you can read them without sudo after a failed run.

triage14
rules for editing the test config

Two rules, then you can add a script

1 — Keep SSHD_PORT: "22" on configure-firewall, setup-sshd and setup-fail2ban. The harness reaches the guest on 22; the scripts' own default (2224) would move sshd or the firewall under the harness and lock the run out mid-suite.
2 — Order matters. setup-basics first (git/yq/jq/node), setup-docker before anything docker-based. Scripts execute in config order.

Adding a new script to the default set

It must be non-interactive without a TTY, safe on a clean VM with the default VM user, and its second run must skip cleanly or genuinely converge — the default set only contains scripts that already satisfy the re-run policy.

--scripts a,b,c does not edit the config

It generates a one-off config in the report dir. Listed scripts keep their env/args; unknown ones get empty env/args — so for SSH-port-related scripts, add them to machine-config.test.yml instead.

The pre-commit lint gate

bash
tests/install-git-hooks.sh            # once: core.hooksPath = tests/git-hooks
tests/install-git-hooks.sh --status   # installed?
tests/install-git-hooks.sh --uninstall
a blocked commit
pre-commit: LINT FAILED — commit blocked
pre-commit:   shellcheck tasks/setup-docker.sh
pre-commit: fix the files, 'git add' them, commit again.
pre-commit: bypass (discouraged): KWISATZ_PRECOMMIT_SKIP=1 git commit …
  • lints the staged content by type: .sh + bash-shebang scripts (shellcheck), .yml (yamllint), .json (jq), .js (node --check), .py (ruff), Dockerfile* (hadolint)
  • then runs tests/lint.sh on every commit (~1 s)
  • fixing a file without staging the fix does not get it through
  • a missing linter fails the commit; hadolint only warns (its image is a network pull)

Versioned in tests/git-hooks/, installed via core.hooksPath — so one install covers every git worktree of the repo, and the hook logic is reviewable in a PR.

Installs once per clone or worktree via core.hooksPath; it lints staged blobs, so fix + git add + commit.

definition of ready

A change is mergeable when…

1

Lint clean. shellcheck for shell, ruff for python — no errors, no warnings.

2

tests/lint.sh passes.

3

VM suite says SUITE: PASS for the scripts you touched — or the default set if you changed the orchestrator, the CLI, or shared lib/. Default --mode cli is the one that counts.

4

Idempotency holds. Phase 2 must pass: the re-run converges, reuses secrets, tears nothing down.

the whole ladder, in order
shellcheck tasks/<changed>.sh && uv run ruff check src tests deploy.py
tests/lint.sh && uv run pytest
tests/run-vm-tests.sh --scripts <what>,<you>,<changed>   # or: no args, for the default set
Phase 2 is the one people skip: it must prove converge, not just a second green run.
