# CONTEXT.md

## Domain Terms

### Infrastructure

- **server** — the AI server machine (remote, for accessing services)
- **workstation** — local developer machine
- **host** — same as **server** in this context (the Ubuntu machine)
- **mixed deployment model** — some services run in docker containers, others run directly on the host
- **compose file** — the `docker-compose.yml` generated by task scripts
- **backend services** — services running behind traefik
- **routes** — traefik routing configuration done via annotations
- **ufw** — firewall on the ubuntu host
- **traefik** — reverse proxy

### Automation

- **task** — a setup script (e.g., `setup-docker.sh`, `setup-llama-swap.sh`)
- **run a task** — execute one single setup script
- **backup-server** — the designated machine that stores the fleet's Borg repositories ("dumb" storage host: no passphrases, no scheduling)
- **backup-client** — any machine that pushes encrypted Borg backups (remote over SSH, or local mode for self-backup)
- **service dump** — an engine-level consistent database snapshot (`pg_dump`/`mysqldump`/`sqlite3 .backup`/`forgejo dump`) staged into a Borg archive before `borg create`, so no archive contains a database copied mid-write
- **library** — the `lib/` directory containing common functionality shared between task scripts
- **template** — configuration file templates in `templates/` that get converted/rendered into actual config files for installed services/tools
- **idempotent** — safe to re-execute (no data loss on repeated runs)
- **version pin** — the exact upstream version (image tag/digest, release, PyPI version, commit) a task installs by default; every pin lives in `versions.yml` and is read with `kw_image` / `kw_version` / `kw_pin` from `lib/helpers.sh`
- **HELD pin** — a version pin Renovate must not move past a major, because the next one breaks persisted data (postgres data dirs, Nextcloud's one-major-at-a-time rule); marked `# HELD` in `versions.yml` and mirrored by an `allowedVersions` rule in `renovate.json`

### AI/ML

- **inference server** — a running model process
- **llama-swap** — proxy for running multiple LLM endpoints via llama-cpp, routes requests between them
- **llama-cpp** — C++ implementation for running LLMs
- **vllm** — high-performance inference engine
- **vllm-omni** — vLLM sub-project extending inference to omni-modality models (TTS, diffusion, image/video generation, any-to-any); served via `vllm serve <model> --omni`
- **nanobot** — long-running AI agent in OpenClaw style
- **whispering** — speech recognition tool for transcribing recorded audio to text
- **model catalog** — the declarative model list (`models.yml`, gitignored, or the committed fallback `models.yml.default`); consumed by `tasks/sync-models.py` to download weights and configure llama-swap and the coding agents' model configs
- **LLM gateway** — the private LiteLLM proxy (`setup-llm-gateway.sh`, `/srv/llm-gateway`, port `4000`) that gives clients one OpenAI/Anthropic-compatible base URL and one key in front of the llama-swap boxes; it picks the box per request, the boxes keep serving their own models
- **deployment** — one backend a gateway model can use: a `backends` entry (box base URL) plus that box's own llama-swap model id and its real `max_parallel`
- **model group** — a public model name in `gateway.yml` mapped to one or more deployments (one box = single deployment, several = load-balanced group)
- **session pin / session affinity** — a client session stays on the deployment that served its first request, so llama-swap does not re-load the model on another box mid-conversation; a pinned session at its deployment's cap gets `429`, it does not spill over
- **resident model** — a model kept loaded (`ttl: 0`) on a llama-swap box; required for every member of a shared model group, since an eviction during a swap costs a full reload
- **break-glass path** — calling a llama-swap box directly on `:9292`, bypassing the gateway, for when routing itself is the problem

### Services

- **forgejo** — self-hosted Git service (fork of Gitea)
- **n8n** — workflow automation tool
- **workflow** — n8n automations
- **netbird** — self-hosted WireGuard-based mesh VPN (management + signal + relay + embedded STUN + dashboard)
- **homeserver** — the Matrix server that stores a team's accounts, rooms and messages; here Synapse (`setup-matrix.sh`)
- **server_name** — the Matrix server name, the part after the colon in `@alice:example.com` (`MATRIX_SERVER_NAME`); immutable once the homeserver exists
- **MAS** — Matrix Authentication Service: the OAuth 2.0/OIDC login, registration and session service Synapse delegates to
- **Element / Element X** — the Matrix clients: Element Web (browser, self-hosted at `chat.<server_name>`) and Element X (iOS/Android)
- **MatrixRTC / LiveKit / lk-jwt-service** — Matrix voice/video calls: MatrixRTC is the call protocol, LiveKit the media server (SFU), lk-jwt-service issues LiveKit tokens to authenticated Matrix users
- **well-known delegation** — `https://<server_name>/.well-known/matrix/{client,server}` documents that point clients and other servers at the real homeserver host
